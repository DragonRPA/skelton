## 채택 원칙 1 — 2x2 시스템 취급 난이도 매트릭스

새 프로젝트를 시작하기 전, 이 매트릭스로 난이도를 먼저 규정한다.
난이도는 기능의 복잡도가 아니라 **누가 어디서 쓰는가**로 결정된다.

|  | 나만 사용 | 타인 사용 |
|---|---|---|
| **로컬** | 최하 — 딸깍 가능. 예외 처리 최소화 | 중간 — 돌발 입력 방어, UX 강화 필요 |
| **원격(클라우드)** | 중간 — API 키 보안, 클라우드 배포 | **최상 — 보안·무결성·동시성 필수** |

**판단 규칙**: 타인이 원격 환경에서 쓰는 순간,
보안(RLS), 에러 복구, 사용성이 치명적 실패 요인이 된다.
설계 단계에서부터 이 전제를 박아야 한다. 데모 이후에 얹으려 하면 늦다.

## 채택 원칙 2 — 5단계 순환 라이프사이클

매일 작동하며 사고를 일으키지 않는 자동화 시스템의 필수 구조.
이 5단계가 파이프라인으로 연결되지 않은 시스템은 **언젠가 반드시 무너진다.**

```
[입력] → [저장] → [처리]
  ↑                  ↓
[복구] ← ← ← ← [표시]
```

| 단계 | 역할 | 실패 시 증상 |
|------|------|-------------|
| 입력 (Input) | 폼·API·웹훅으로 안전하게 주입 | 잘못된 데이터 유입 |
| 저장 (Storage) | 스키마 무결성 보장 DB 영구 기록 | 데이터 유실·중복 |
| 처리 (Processing) | 비즈니스 로직·외부 연동 비동기 실행 | 결제 실패·알림 누락 |
| 표시 (Display) | 실시간 상태 클라이언트 반영 | 화면과 DB 불일치 |
| **복구 (Recovery)** | 실패 시 롤백·자동 재시도 | **무음 실패, 데이터 파괴** |

> 기존 글로벌 정책(5.2 Zero Silent Failures)의 철학적 근거가 여기에 있다.
> "복구" 단계가 없으면 실패는 반드시 무음으로 삼켜진다.

## 채택 원칙 3 — 하네스(Harness) 엔지니어링

> **"AI의 지능은 확률이다. 운영 환경에서 확률은 사고다."**

AI 행동을 위험도로 분류하고, 위험한 행동에는 인간 승인 게이트를 건다.

| 위험 수준 | 행동 유형 | 통제 방식 |
|-----------|-----------|-----------|
| 낮음 | 읽기·요약·조회 | AI 자율 허용 |
| 중간 | 초안 생성·분류·정렬 | 결과 검토 후 반영 |
| **높음** | 수정·삭제·발송·결제·DB 반영 | **`PENDING_APPROVAL` 대기 → 인간 클릭 승인 후 실행** |

**구현 원칙**:
- 파괴적·재무적 행동의 API는 즉시 실행하지 않는다
- `status: 'PENDING_APPROVAL'`로 DB에 임시 저장
- 관리자 화면에서 인간이 승인/반려한 후에만 실제 실행
- 실행 로그는 반드시 보존 (추적 가능성 = Audit Trail)

> 이것은 글로벌 정책 카테고리 I의 "발생되는 사건 기록의 무누락 DB 저장"과
> 동일한 철학이다. 바이브 코딩에서도 이 원칙은 변하지 않는다.
