# 1회 발송된 이메일의 재발송(Re-send) 업무 설계 및 아키텍처 표준

---

## 🏛️ 1. 문제의 본질 및 설계 목적 (Core Mission)
- **최우선 사명 (헌장 1.1)**: "최대 편리함과 담당자의 노력 대비 효과와 이익(최대 편익) 달성"
- **실무 현장의 마찰**:
  1. 고객사 담당자의 메일 분실, 스팸함 격리, 담당자 퇴사/변경 등으로 인한 재발송 요청 빈번.
  2. 단순 '재발송' 버튼만 누르면 고객사는 "이중 청구인지, 수정본인지, 단순 재송부인지"를 알 수 없어 정산이 지연됨.
  3. "누가, 언제, 왜, 어떤 내용으로 다시 보냈는가"에 대한 감사 추적성(Audit Trail)이 없으면 분쟁 발생 시 법적/회계적 증빙 불가.
- **설계 목적**: 
  - 실무자의 재입력 노력을 0으로 줄이는 **1-Click 컨텍스트 자동 상속(Pre-fill)**.
  - 고객사의 혼선을 원천 방지하는 **발송 목적별 스마트 제목/본문 자동 조합**.
  - 1원과 1초의 오차도 없는 **발송 차수(Sequence)별 불변 스냅샷 이력 DB 저장**.

---

## 🧭 2. 재발송 3대 표준 유형 분류 (3-Type Classification)

모든 재발송 업무는 아래 3가지 유형 중 하나로 명확히 귀속된다:

| 구분 | 업무 상황 (Trigger) | 이메일 제목 표기 표준 | 본문 상단 시스템 안내 배너 |
|---|---|---|---|
| **유형 1: [단순 재송부]** | 고객 미확인, 분실, 스팸함 격리, 담당자 변경 | `[재발송] {원제목}` | "본 메일은 거래처 요청으로 재송부된 안내 메일이며, 기존 발행된 청구 내역과 동일합니다." |
| **유형 2: [정정/수정 재발송]** | 날짜/단가/금액 정정, 증빙서류 누락 보완 | `[정정재발송] {원제목}` | "⚠️ 기존 발행된 내역에 일부 정정(변경) 사항이 반영된 정정 청구서이오니 확인 바랍니다." |
| **유형 3: [입금 독촉/리마인드]** | 결제기한 도래/경과, 미납 상태 안내 | `[납부안내/재송부] {원제목}` | "약정 결제일이 도래(경과)하여 미납 청구 내역을 재안내드리오니 입금 확인 부탁드립니다." |

## ⚙️ 3. 실무자 3단계 업무 파이프라인 (3-Step Interaction Pipeline)

```
[1단계: 재발송 클릭] ➔ [2단계: 유형 선택 & 수신처 스코핑] ➔ [3단계: 스마트 발송 & 스냅샷 저장]
```

### 1단계: 이전 발송 컨텍스트 100% 자동 상속 (Zero-Input Pre-fill)
- 실무자가 청구서 대장 또는 계약 대장에서 `[재발송]` 버튼 클릭.
- 직전 발송된 **수신자 이메일, 참조(CC), 제목, 본문, 첨부파일(PDF 스냅샷)**이 모달 폼에 100% 자동으로 채워져 로딩.

### 2단계: 수신처 스코핑 (1회성 발송 vs 마스터 영구 갱신 분기)
- **상황**: 고객사가 "이번 건만 `account2@customer.com`으로 보내주세요"라고 하거나 "담당자가 바뀌었으니 앞으로 여기로 보내주세요"라고 할 때.
- **체크박스 제공**: `☑️ 고객사 기본 수신 이메일 마스터에도 함께 반영`
  - 체크 시: 고객사 마스터(`customers.repEmail`)도 동시에 영구 갱신.
  - 미체크 시: 이번 1회성 재발송에만 임시 적용 (마스터 불변 보존).

### 3단계: 스마트 머릿말 자동 삽입 & 차수 누적 불변 저장
- 실무자가 유형(단순재송부 / 정정재발송 / 입금독촉) 라디오 버튼을 선택하면:
  - 메일 제목 머릿말(`[재발송]`, `[정정재발송]`)이 자동 접두어로 결합.
  - 본문 최상단에 표준 안내문이 자동 삽입.
- 발송 실행 즉시:
  - `email_dispatch_logs`에 **`sendSequence: 2` (2차 발송)** 기록.
  - 대장 행(Row) 배지가 `✉️ 발송완료 (1차)` ➔ `✉️ 재발송완료 (2차)`로 실시간 전이.

## 🗄️ 4. 데이터 모델 설계 (Audit Trail Schema)

```sql
-- 이메일 발송/재발송 이력 마스터 테이블
CREATE TABLE email_dispatch_logs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_type VARCHAR(50) NOT NULL, -- 'BILLING', 'CONTRACT', 'ASSET_SALE', 'DELINQUENCY'
    entity_id VARCHAR(100) NOT NULL,   -- billingId, contractId 등
    send_sequence INT NOT NULL DEFAULT 1, -- 발송 차수 (1, 2, 3...)
    send_type VARCHAR(30) NOT NULL,    -- 'INITIAL', 'RESEND_SIMPLE', 'RESEND_REVISED', 'RESEND_REMIND'
    resend_reason TEXT,                 -- 재발송 사유 (예: "고객사 담당자 변경 요청")
    sender_user_id VARCHAR(50) NOT NULL, -- 발송 임직원 ID
    recipient_to TEXT NOT NULL,         -- 수신자 (to)
    recipient_cc TEXT,                  -- 참조자 (cc)
    subject TEXT NOT NULL,              -- 실제 전송된 메일 제목
    body_text TEXT,                     -- 실제 전송된 메일 본문
    attachment_name TEXT,               -- 첨부파일명
    attachment_storage_url TEXT,        -- 발송 당시의 불변 첨부파일 스냅샷 경로
    is_master_synced BOOLEAN DEFAULT FALSE, -- 고객사 마스터 이메일 동기화 여부
    sent_at TIMESTAMPTZ DEFAULT NOW()   -- 발송 일시
);

-- 인덱스
CREATE INDEX idx_email_dispatch_entity ON email_dispatch_logs(entity_type, entity_id);
CREATE INDEX idx_email_dispatch_sent_at ON email_dispatch_logs(sent_at DESC);
```

## 🛡️ 5. 휴먼 에러 방어 3대 안전 가드 (Safety Guards)

1. **중복 클릭(Double Send) 원천 방어**:
   - 실무자가 메일 발송 버튼을 연타하거나, 다른 직원이 동일 건을 5분 이내에 재발송하려 할 때:
   - "⚠️ 3분 전 이미 동일 수신자(account@xxx.com)에게 발송된 내역이 있습니다. 정말 다시 발송하시겠습니까?" 경고 확인창 표출.
2. **수납 완료(PAID) 건의 입금 독촉 재발송 차단**:
   - 이미 통장 매칭(BankMatching)으로 수납 완료된 청구서에 대해 '입금 독촉' 유형 재발송 시도 시:
   - "⚠️ 해당 건은 이미 2026-09-02 완납된 청구서입니다. 입금 독촉 메일은 발송할 수 없습니다." 원천 차단.
3. **무효 이메일 형식 사전 정규식 검증**:
   - 쉼표(,) 구분 복수 이메일 입력 시 공백 제거 및 정규식 검증을 통과해야만 발송 버튼 활성화.
