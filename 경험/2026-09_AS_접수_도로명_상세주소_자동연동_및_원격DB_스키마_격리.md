# 경험: AS 접수 도로명 상세 주소 실시간 자동 역추적 및 원격 DB 스키마 격리/백업 아키텍처

- **일시**: 2026-09-04 16:55
- **프로젝트**: Kiyeun_Lift (고소작업대 렌탈 ERP)
- **카테고리**: 경험 (EXPERIENCE)
- **관련 커밋**: Build.134 (`c9f72e3`)
- **경험.md 이슈 ID**: E-053

---

## 1. 상황 (Context)
- 외근 AS 정비 기사가 스마트폰 PWA에서 [T맵 길안내]를 실행할 때, 구체적인 시/군/구 도로명 주소가 전달되지 않고 단순 현장명(예: 'SK 팹동')만 전달되어 T맵에서 목적지 탐색이 실패하거나 모호한 검색 결과가 나오는 문제가 발생함.
- 원인 규명 결과, AS 접수(인테이크) 단계에서 장비번호나 고객사 정보를 입력받을 때 도로명 상세 주소를 연동하지 않고 있었음.
- 또한 원격 Supabase DB의 `repairs` 테이블에는 `siteAddress` 컬럼이 실재하지 않아, 무작정 컬럼을 전송할 경우 PostgreSQL 42703 거부 오류가 발생하는 스키마 비대칭 난제가 있었음.

---

## 2. 해결 전략 (Action)
1. **인테이크 엔티티 체인 실시간 자동 역추적 (`MobileAsCreate.tsx`, `FieldAsManagement.tsx`)**:
   - `assetNo` 입력 즉시 `assets ➔ contractAssets ➔ contracts ➔ customerSites/customers`를 1초 만에 실시간 역추적하여 고객사명, 현장명, 상세 도로명 주소를 자동 완성.
   - 고객사 선택 시 등록된 현장 목록 퀵 칩 표출 및 1-Click `[고객사 주소 적용]` 헬퍼 지원.
   - 전사 UI 표준 헌장 3.4(상하 세로 스택) 및 3.1(건조한 명사: `현장 도로명 주소`) 100% 준수.
2. **원격 DB 스키마 격리 및 무누락 백업 레이어 (`db.ts`, `AppContext.tsx`)**:
   - `sanitizeSupabasePayload`에서 `repairs.siteAddress`를 격리하여 PostgreSQL 42703 에러 원천 차단.
   - 원격 DB의 기존 컬럼인 `locationDetail` 또는 `memo`에 `[현장도로명: ...]` 형태로 무누락 백업.
   - `db.repairs` getter에서 Supabase 로드 시 메모/상세위치를 자동 파싱하여 `siteAddress`를 투명 복원.
3. **내비게이션 유틸리티 SSOT 확립 (`nativeLauncher.ts`)**:
   - `resolveSiteDetailedAddress`에 `siteAddress`를 최우선 0순위로 채택하고, 고객사 마스터 등록 주소까지 역추적을 확장.

---

## 3. 배운 점 (Learning)
- **현장 데이터의 자동 상속 원칙**: 렌탈 업무에서 장비번호 하나만 알아도 활성 계약과 고객사, 현장 주소까지 100% 도출될 수 있다. 사용자가 번복 입력하지 않도록 엔티티 관계망을 실시간 탐색하여 자동 완성해주는 것이 헌장 1.1의 '최대 편익'을 달성하는 길이다.
- **클라우드 스키마 진화와 격리 패턴**: 프론트엔드/로컬 모델의 빠른 진화와 원격 관계형 DB 스키마 간의 시차(Time lag)를 안전하게 극복하기 위해, 미반영 컬럼의 페이로드 필터링 및 텍스트 백업 필드로의 투명 복원 레이어를 구축하는 것이 무음 실패나 트랜잭션 오류 없는 완벽한 무중단 배포를 보장한다.
