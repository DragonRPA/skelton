설계 단계에서 수립한 5계층 비렌탈 도메인 차단과 별도로, 영향도 검토 과정에서 식별된 **공유 Hub DB(`fl_*`) 멀티테넌트 `tenant_id` 행 격리 과제**까지 함께 완결하고 양대 프로덕션 배포를 마쳤다.

## 3대 아키텍처 교훈

### 1. 게이트웨이 프록시 기반 `tenant_id` 행 격리 + PostgreSQL 복합 유니크 전환
- **한계 발견**: 모든 `fl_*` 테이블에 `tenant_id NOT NULL` 컬럼이 존재했음에도, 앱 전역 90여 DB 호출부가 `.eq('tenant_id', ...)` 조건 없이 조회/수정하고, 16개 업무 번호 컬럼(`login_id`, `action_code`, `sku`, `contract_no` 등)이 전역 단일 컬럼 `UNIQUE`로 걸려 있어 2번 테넌트 등록 시 즉시 충돌할 구조였다.
- **해결 원칙**:
  1. [supabase.ts](file:///D:/01.AntiGravity/ebro_FL/src/core/supabase.ts)의 `flSupabase` 게이트웨이(`.from`)를 프록시로 감싸 운영 테이블(`fl_*`, 백업 제외)의 모든 `select`/`insert`/`upsert`/`update`/`delete`에 활성 `tenant_id` 필터와 스탬프를 100% 자동 주입했다.
  2. [AppShellContext.tsx](file:///D:/01.AntiGravity/ebro_FL/src/core/AppShellContext.tsx) `refreshAll()`에서 **테넌트 식별 ➔ [ensureFlTenantBootstrapped](file:///D:/01.AntiGravity/ebro_FL/src/services/domainEngine.ts) 자동 시드(루트 부서 · 초기 Tier-7 관리자 · 13종 결재 기준 · 5종 문서 양식) ➔ 전 테이블 적재** 순서를 강제해 병렬 부팅 레이스 컨디션을 제거했다.
  3. [migrate_fl_multitenant_isolation.cjs](file:///D:/01.AntiGravity/ebro_FL/scripts/migrate_fl_multitenant_isolation.cjs) 및 [schema.sql](file:///D:/01.AntiGravity/ebro_FL/schema.sql)을 통해 전역 단일 컬럼 `UNIQUE` 16종 및 `fl_document_templates(doc_type)`을 모두 `UNIQUE (tenant_id, ...)` 복합 제약으로 전환하고 30개 운영 테이블에 `tenant_id` 인덱스를 구축했다.
  4. [ManualContext.tsx](file:///D:/01.AntiGravity/ebro_FL/src/manual/ManualContext.tsx)의 `core_manual_annotations` 역시 공통 기본 행(`tenant_id IS NULL`) 위에 테넌트 전용 행(`tenant_id`)을 계층 오버라이드하도록 격리하고, 브라우저 `localStorage` 세션 키도 테넌트별로 분리했다.

### 2. 부분 도메인 배제 하에서도 대차/현금 보존 법칙(`balanceDiff === 0`, `cashCheckDiff === 0`) 유지
- `generateFinancialStatements(..., { includeRental })` 구현 시 표시 라인만 숨기면 복식부기 균형이 붕괴한다.
- 원천 이벤트 단계에서 렌탈 매입·감가상각·금융리스·전대·렌탈 청구/수납 및 관련 지급 분개 자체를 쌍(차변+대변)으로 배제하고, 실 DB(매입 23건 · 자산/재고 194건 · 청구 133건) 및 혼합 스트레스 데이터 양쪽에서 `includeRental: true / false` 모두 `balanceDiff = 0`, `cashCheckDiff = 0`을 실측 입증했다.

### 3. 비렌탈 전환 시 기존 `ACCOUNT_TRANSFER` 유통 원천 재고 복원 (`isEffectiveTradeUnitForTenant`)
- 과거 렌탈 영업 당시 유통 재고를 렌탈 자산으로 계정대체했던 테넌트가 추후 비렌탈로 전환할 경우, 해당 장비가 유통 재고 화면·실사·출고에서 고아 자산으로 증발할 위험이 있었다.
- `stock_movements`의 최초 `INBOUND` 또는 `ACCOUNT_TRANSFER` 이력을 추적해 최초 원천이 유통인 자산을 비렌탈 모드에서 유효 유통 재고로 노출하고, `completeFulfillment` 실행 시 DB `ownership_domain = '유통재고'`로 정규화해 판매/출고 마감까지 막힘없이 완결되도록 처리했다.
