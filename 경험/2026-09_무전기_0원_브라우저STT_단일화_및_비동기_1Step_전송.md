# 🎙️ 무전기 0원 브라우저 STT 단일화 및 비동기 1-Step 전송

- **기록일시**: 2026-09-04 20:54
- **작성버전**: `v1.3.0.Build.135`
- **관련 프로젝트**: `Kiyuen_Lift` (`walkieTalkieService.ts`, `MobileWalkieTalkieModal.tsx`, `api/gemini-stt.ts`)

---

## 1. 배경 및 기술적 난관

1. **외부 유료 API(Gemini STT) 과금 리스크 문제**:
   - 무전기(PTT)에서 음성 전사를 위해 외부 유료 API를 사용할 경우, 일상적인 짧은 음성 수백 회 호출 시 개발자 계정 및 회사에 예상치 못한 과금이 발생함.
   - 사장님의 '비용 0원 원칙'에 따라 모든 외부 과금 API를 영구 배제하기로 결정.
2. **모바일 브라우저(Android Chrome) 마이크 독점 충돌 (`empty transcript`)**:
   - Web Speech API(`SpeechRecognition`)와 `MediaRecorder`(`getUserMedia`)를 동시에 실행할 때, `getUserMedia`가 마이크를 먼저 잡으면 브라우저 STT 엔진이 마이크 장치 잠금으로 인해 무음 처리되거나 빈 문자열(`""`)을 반환하는 현상 발생.
3. **동기식 종료로 인한 마지막 발언 유실**:
   - 발언 종료 버튼을 뗄 때 STT 종료 처리가 동기식으로 즉각 변수를 읽어버려, 구글 음성 서버/로컬 엔진이 마지막 단어를 텍스트로 확정하기도 전에 빈 텍스트를 전송함.
4. **순서 뒤죽박죽 전송 파이프라인**:
   - 음성 메시지를 먼저 브로드캐스트하고, 수 초 뒤에 STT 결과를 별도 메시지로 업데이트하여 수신자 화면에 깜빡임과 순서 혼선이 발생함.

## 2. 해결 방법론 (3대 핵심 아키텍처)

1. **마이크 세션 선점 (실행 순서 역전)**:
   - `startRecording()` 시점에 `getUserMedia`보다 `startBrowserRecognition()`을 0순위로 먼저 호출.
   - 브라우저 STT 세션을 먼저 열어놓은 뒤 오디오 녹음 스트림을 받음으로써, 크롬 브라우저가 동일 마이크 입력을 두 파이프라인(STT + 녹음)으로 정상 분기(Multiplexing)하도록 유도.
2. **비동기 완료 보장 대기 (`Promise` + `onend` + 500ms 안전 타임아웃)**:
   - `stopBrowserRecognition()`을 `Promise<string>` 구조로 개편.
   - 사용자가 손을 뗄 때 STT에 정지 신호(`rec.stop()`)를 보내고, 엔진의 최종 문장 변환 이벤트(`onend`)를 최대 500ms 동안 비동기로 안전 대기하여 마지막 발언까지 100% 회수.
3. **음성 + 텍스트 1-Step 일괄 전송**:
   - 비동기로 회수된 텍스트(`transcriptText`)를 녹음된 음성 데이터와 함께 처음부터 1개의 단일 메시지 객체(`msg.textTranscript`)로 통합 패키징.
   - 단 1번의 브로드캐스트로 음성과 자막이 발신자/수신자 화면에 동시에 표출되도록 순서를 완벽히 일원화.
4. **디버그 로그 사용자 제어 토글**:
   - 모바일 화면 상단에 `[디버그OFF / 🐞 디버그ON]` 버튼을 배치하여 실시간 진단 로그를 사용자가 선택적으로 확인 가능하도록 구현 (기본 OFF).

## 3. 핵심 교훈 및 재발 방지 원칙

- **웹 브라우저 STT는 스트리밍 전용**: 파일 기반 STT(Whisper 등)와 달리, 브라우저 Web Speech API는 오디오 파일을 입력받지 못하며 오직 살아있는 마이크 스트림만 입력받음. 따라서 녹음 도중 동시에 스트리밍 방식으로 처리해야 함.
- **마이크 자원 순서 중요성**: 안드로이드 크롬 환경에서는 `SpeechRecognition`을 `getUserMedia`보다 먼저 초기화해야 하드웨어 오디오 스트림 잠금 충돌을 회피할 수 있음.
