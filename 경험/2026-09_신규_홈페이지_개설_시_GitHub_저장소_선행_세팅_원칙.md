# 🔬 [경험] 신규 홈페이지(웹사이트) 프로젝트 구축 시 GitHub 저장소 선행 세팅 원칙 (이중 작업 방지)

- **작성일자**: 2026-09-28
- **관련 프로젝트**: 전사 웹 프로젝트 (dragonrpa.co.kr, ERP 포털, 신규 랜딩페이지 등)
- **카테고리**: 경험 (EXPERIENCE) & 후회 (REGRET) 교훈
- **주체**: 사장님 & AI 어시스턴트

---

## 1. 개요 및 배경

과거 신규 홈페이지나 웹 서비스를 새로 구축할 때, 프레임워크 설치나 화면 개발에 먼저 착수했다가 **GitHub 저장소 세팅(git init, 원격 저장소 생성, remote 연결, .gitignore 구성)을 사전에 해두지 않아 동일한 작업을 두 번 번복(이중 작업)했던 뼈아픈 경험**이 존재함.

---

## 2. 사후 깃 세팅 시 발생하는 문제 및 이중 작업 원인

1. **원격 저장소와의 히스토리 충돌 (Unrelated Histories)**:
   - 로컬에서 프로젝트 뼈대를 다 만들어 둔 상태에서 GitHub에 새 리포지토리를 만들고 연결할 때, 원격의 기본 파일(README.md, LICENSE 등)과 로컬 커밋 간의 충돌(`fatal: refusing to merge unrelated histories`)이 발생하여 브랜치를 강제로 맞추거나 리베이스하는 번거로운 복구 작업 발생.
2. **`.gitignore` 누락으로 인한 빌드 부산물 오염**:
   - Git 세팅 없이 `npm install`이나 빌드를 먼저 진행하다가 `node_modules`, `.next`, `dist`, `.env` 등 민감 정보나 대용량 캐시 파일이 Git 인덱스에 포함되어, 이를 추적 해제(`git rm -r --cached`)하고 커밋을 되돌리는 불필요한 공수 발생.
3. **배포 파이프라인(Vercel, Cloudflare Pages 등) 연동 지연**:
   - 깃허브 리포지토리가 초기에 연결되어 있지 않으면 CI/CD 빌드 성공 여부를 실시간으로 검증하지 못하고, 배포 단계에서 뒤늦게 환경설정 오류나 빌드 실패가 터져 나와 디버깅 시간이 2배로 증가함.

## 3. GitHub-First 불변의 4단계 초기 세팅 원칙 (Checklist)

신규 홈페이지나 웹 프로젝트를 시작할 때는 **코드 1줄을 작성하거나 템플릿을 풀기 전에 반드시 아래 'GitHub-First' 절차를 제0단계로 완결**한다:

```
[0단계: GitHub-First] ──► [1단계: 프레임워크 셋업] ──► [2단계: CI/CD 검증] ──► [3단계: 본 개발 착수]
 GitHub 원격 리포 생성      Next.js / Vite 설치      Vercel / Cloudflare 연결     컴포넌트 및 비즈니스
 git init & remote 연결    .gitignore 최우선 점검     최초 빌드·푸시 성공 확인       UI/UX 본격 구현
```

1. **GitHub 원격 저장소 생성**:
   - `DragonRPA` 또는 개인 계정에 리포지토리를 먼저 생성 (충돌 방지를 위해 초기 README/License 자동 생성 옵션 체크 해제 권장).
2. **로컬 디렉토리 `git init` 및 원격 연결**:
   ```bash
   git init
   git remote add origin https://github.com/DragonRPA/<repo-name>.git
   git branch -M main
   ```
3. **`.gitignore` 최우선 구성 및 최초 커밋(Initial Commit)**:
   - 프레임워크 설치 전후로 `.gitignore`를 즉각 확립하여 `.env`, `node_modules` 배제를 보장한 후 `feat: initial commit` 푸시.
4. **배포 환경(Vercel / Cloudflare) 즉시 연결**:
   - 첫 번째 커밋이 푸시되는 즉시 배포 파이프라인에 연결하여 '빈 화면 정상 배포' 상태를 먼저 확보.

>
