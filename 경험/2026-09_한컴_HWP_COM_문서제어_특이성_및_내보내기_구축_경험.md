## 1. 구현 배경 및 타 프로그램 대비 체감 난이도

매뉴얼 스튜디오는 화면 캡처 및 주석 작업 결과를 다양한 외부 문서 도구(PowerPoint, Google Slides, MS Word, PDF, WebBook, Markdown)로 원클릭 내보내는 엔진을 탑재하고 있다.
대다수의 타 프로그램(PPT, Word 등)은 비교적 수월하게 레이아웃과 서식이 정밀 제어된 반면, **한컴오피스 한글(HWP)의 경우 의도와 다르게 작동하는 다수의 예외와 마찰이 집중 발생**하였다.

타 오피스 프로그램 대비 HWP 형식 제어가 까다롭고 의도대로 작동하지 않았던 기술적 원인과 현장 경험을 기록하여, 향후 RPA 및 오피스 자동화 엔진 개발의 표준 교훈으로 삼는다.

## 2. HWP 형식 제어가 의도대로 작동하지 않았던 6대 핵심 원인

### 1) 객체 지향 모델(DOM) vs 텍스트 스트림/파라미터셋(HParameterSet)의 패러다임 괴리
- **PowerPoint / MS Word**:
  - 완벽한 객체 지향(OOP DOM) 계층을 제공한다.
  - 슬라이드나 페이지 객체에서 `Shapes.AddPicture(Path, Left, Top, Width, Height)`를 호출하면, 대상 이미지의 좌표와 크기를 포인트(`pt`) 단위로 즉시 확정할 수 있다.
  - 제목 상자(`TextBox`)와 이미지(`Picture`)가 서로 독립된 2D 평면 레이어로 존재하여 상호 간섭이 없다.
- **한컴 HWP**:
  - 전통적인 워드프로세서로서 **본문 커서 위치 중심의 텍스트 스트림 아키텍처**를 가진다.
  - 이미지를 삽입할 때 `ShapeObject` 핸들을 직접 반환받아 속성을 설정하는 것이 아니라, 커서가 위치한 문단에 조판부호 또는 글자처럼 취급(Inline)되어 삽입된다.
  - 이미지의 속성을 바꾸려면 `HAction.GetDefault` ➔ `HParameterSet` 조작 ➔ `HAction.Execute`라는 간접 액션 방식을 거쳐야 하며, 커서 포커스 상태나 문서 내부 상태에 따라 파라미터가 무시되거나 실패하기 쉽다.

### 2) `FileNew` 트랩과 다중 창(Process Window) 분열 버그
- **문제 현상**: HWP 내보내기를 실행할 때마다 빈 한글 프로그램 창 1개와 작업용 한글 프로그램 창 1개, 총 **2개의 한글 창이 동시에 뜨는 현상**이 발생했다.
- **원인 분석**:
  - `win32com.client.Dispatch("HWPFrame.HwpObject")`로 객체를 생성할 때, HWP는 이미 빈 기본 문서(Document 1)를 가진 윈도우 인스턴스를 즉시 띄운다.
  - 통상적인 습관으로 초기화를 위해 `hwp.HAction.Run("FileNew")` 또는 `hwp.FileNew()`를 호출하면, 기존 문서를 닫지 않고 **새로운 프로세스 창(Document 2)을 별도로 띄워버려 창이 복제 분열**된다.
  - 또한 기존에 열어둔 인스턴스를 전역 변수나 인스턴스 멤버(`self._hwp_instance`)로 유지하지 않고 매 내보내기마다 `Dispatch`를 남발하면 한글 프로세스가 기하급수적으로 중복 생성된다.

### 3) 독자적인 단위계(HwpUnit)와 가로(Landscape) 용지 여백 설정의 불일치
- **단위계의 이질성**:
  - 일반 그래픽/웹은 `px`, PPT/Word는 `pt` (1/72 inch)를 표준으로 사용한다.
  - HWP는 내부 엔진에서 **`HwpUnit` (1 inch = 7,200 HwpUnit, 즉 1 pt = 100 HwpUnit, 1 mm ≒ 283.465 HwpUnit)**이라는 독자 단위계를 사용한다.
- **가로 용지 및 여백 설정 실패**:
  - 슬라이드 매뉴얼은 16:9 규격이므로 A4 가로(297mm × 210mm) 배치가 필수적이다.
  - `PageDef` 파라미터셋에서 `Landscape = 1`을 지정하고, `PaperWidth = 297 * 283.465`, `PaperHeight = 210 * 283.465`, `LeftMargin`, `RightMargin` 등을 모두 HwpUnit 단위로 정확히 계산하여 `PageSetup` 액션을 실행해야만 비로소 가로 문서로 셋팅된다.
  - 단위 환산이 1포인트라도 틀어지거나 액션 실행 순서가 어긋나면 문서가 세로(Portrait) 상태로 남아 이미지가 찌그러지거나 잘리는 현상이 발생했다.

### 4) 문단 정렬(Paragraph Alignment)과 인라인 이미지의 종속성 충돌
- **문제 현상**: 문서를 보기 좋게 정렬하기 위해 가운데 정렬(`AlignType = 3`)을 적용했더니, 상단의 `Step 1. [단계명]` 제목 텍스트까지 페이지 한가운데로 밀려나 어색해지고, 반대로 왼쪽 정렬(`AlignType = 1`)을 두면 이미지가 좌측 여백에 치우쳤다.
- **원인 분석**:
  - PPT에서는 제목 텍스트 박스와 이미지가 독립 좌표를 가지므로 제목은 좌측 상단(`Left=50, Top=22`), 이미지는 정중앙에 자유 배치할 수 있다.
  - HWP에서는 텍스트와 이미지가 동일한 본문 문단 흐름에 존재하므로, 문단 서식을 공유하게 된다.
  - 제목 바로 뒤에 이미지를 넣으면 제목 문단의 정렬 속성이 이미지까지 지배하여 서식 충돌이 발생했다.

### 5) 비트맵 투명 여백(액자 프레임 패딩)과 한글 조절 핸들(파란 점)의 시각적 착시
- **문제 현상**: 한글 문서에 삽입된 이미지를 마우스로 클릭하면, 실제 캡처 화면 사방으로 약 40px 정도 떨어진 외곽에 파란색 조절점(Bounding Box 핸들)이 찍히고, 인쇄 여백 외에도 자체적인 여백이 생겨 화면이 작게 출력되었다.
- **원인 분석**:
  - 매뉴얼 스튜디오에 내장된 '창틀 & 소프트 섀도우(액자 프레임, `enable_window_frame`)' 기능이 기본 활성화되어 있었다.
  - 이 기능은 macOS 창틀 헤더(32px)와 부드러운 가우시안 블러 드롭 섀도우를 표현하기 위해 비트맵 사방에 `pad_x = 40px`, `pad_y = 46px`의 투명 알파 패딩을 합성한다.
  - PPT나 Google Slides에서는 투명 여백이 슬라이드 배경과 자연스럽게 녹아들어 문제되지 않았으나, **한컴 HWP는 비트맵의 물리적 바운딩 박스를 기준으로 사방 8개 파란 조절점을 표시**한다.
  - 한글이 투명 여백까지 포함된 전체 비트맵 크기 기준으로 인쇄 폭(277mm)에 맞추다 보니, 투명 영역만큼 실제 캡처 화면이 축소되고 불필요한 공백이 생겼던 것이다.

### 6) 다중 슬라이드 일괄 내보내기 시 선택 스코프(Selection Scope) 판단 누락
- **문제 현상**: 프로젝트에 슬라이드가 8개 이상 존재하는데도 'HWP 내보내기'를 누르면 단 1페이지만 출력되고 끝나는 현상이 발생했다.
- **원인 분석**:
  - 내부 로직의 `get_export_target_steps()`가 슬라이드 필름스트립에서 단일 슬라이드가 포커스된 상태를 "1개만 선택된 상태"로 오판하여 단일 슬라이드만 반환했다.
  - 사용자가 명시적으로 다중 선택(체크박스/Ctrl+클릭)을 하지 않은 채 '전체 내보내기' 메뉴를 누른 경우, 프로젝트의 모든 슬라이드를 전수 타깃으로 삼아야 한다는 도메인 업무 맥락이 누락되어 있었다.

## 3. 실무적 극복 솔루션 및 아키텍처 원칙 (Learnings)

### 1) 단일 HWP 인스턴스 캐싱 및 `FileNew` 호출 전면 금지
```python
# 1. 기존 인스턴스 생존 여부 점검 (단일 창 재사용)
if getattr(self, "_hwp_instance", None) is not None:
    try:
        if self._hwp_instance.XHwpWindows.Count > 0:
            hwp = self._hwp_instance
    except Exception:
        self._hwp_instance = None

# 2. 부재 시에만 Dispatch 최초 실행 (FileNew 호출 절대 금지)
if hwp is None:
    hwp = win32com.client.Dispatch("HWPFrame.HwpObject")
    hwp.XHwpWindows.Item(0).Visible = True
    self._hwp_instance = hwp
```
- `FileNew()`를 호출하지 않고 `Dispatch` 직후 생성된 첫 번째 윈도우(`XHwpWindows.Item(0)`)를 그대로 작업 창으로 사용함으로써 2개 창이 뜨는 버그를 원천 차단함.

### 2) 엄격한 HwpUnit 단위 환산 및 A4 가로 인쇄 영역(277mm) 최대 활용
- A4 가로(297mm × 210mm) 기준, 좌우 여백을 각각 10mm(2835 HwpUnit)로 최소화하여 **순수 인쇄 가능 가로 폭을 277mm(78,520 HwpUnit) 확보**.
- 이미지 크기를 인쇄 가능 폭인 277mm에 정확히 일치하도록 스케일링하여 전송함으로써, 여백 낭비 없이 캡처 화면을 시원하게 배치함.

### 3) 제목 문단과 이미지 문단의 분리(`BreakPara`) 및 정렬 직교화
```python
# 1. 단계 제목 문단: 왼쪽 정렬 (AlignType = 1)
hwp.HAction.Run("ParagraphShapeAlignLeft")
# 2. 문단 강제 분리 (제목과 이미지 서식 격리)
hwp.HAction.Run("BreakPara")
# 3. 이미지 삽입 후 다음 슬라이드 페이지 분할 (마지막 장 제외)
if break_page:
    hwp.HAction.Run("BreakPage")
```
- 제목과 이미지를 별개의 문단으로 분리하여, 제목은 좌측 상단에 정갈하게 배치되고 이미지는 전체 폭을 채우도록 서식을 직교 분리함.

### 4) 워드프로세서 문서용 순수 비트맵 전송 원칙 (`enable_window_frame: False`)
- 한글(HWP) 및 워드(DOCX) 등 규격화된 문서 편집기 대상 프로필에는 `enable_window_frame: false`를 기본값으로 적용.
- 투명 가우시안 그림자 패딩(40px)을 제거한 **순수 1:1 캡처 원본 비트맵**만을 전송하여, 한글 내 조절점(파란 점)이 실제 캡처 화면 테두리에 정확히 밀착되고 문서 영역을 100% 꽉 채우도록 개선함.

### 5) 사용자 의도 기반 타깃 스텝 자동 승계 (`get_export_target_steps`)
- 다중 선택이 없더라도 단일 슬라이드만 잡혀 있는 경우 프로젝트 전체 슬라이드로 자동 확장하여, "8개 중 1개만 출력되는 불상사"를 방지하고 사용자의 의도대로 전수 일괄 출력을 보장함.

## 4. 향후 HWP COM 자동화 개발 시 필수 체크리스트

1. **프로세스 생명주기**: `FileNew`를 호출하지 않는가? `XHwpWindows.Count`로 기존 창을 재사용하고 있는가?
2. **보안 모듈 등록**: `RegisterModule("FilePathCheckDLL", "FilePathCheckerModule")`이 선행되어 보안 팝업 차단이 보장되는가?
3. **단위 환산 정합성**: 모든 여백과 너비/높이에 `HwpUnit (mm × 283.465)` 환산이 정밀하게 적용되었는가?
4. **서식 분리**: 제목 텍스트와 이미지 사이에 `BreakPara`가 실행되어 문단 속성이 상호 오염되지 않는가?
5. **이미지 여백 순수성**: 비트맵 자체에 투명 패딩이나 불필요한 그림자가 포함되어 바운딩 박스 왜곡을 일으키지 않는가?
6. **페이지 종료 처리**: 마지막 슬라이드 뒤에 불필요한 `BreakPage`가 들어가 빈 백지 페이지가 생성되지 않는가?
