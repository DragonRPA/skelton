## 솔직한 회고 — 다시 한다면 무엇을 다르게 하겠는가

### 1. 첫 줄의 코드를 작성하기 전에 GitHub 저장소부터 만들었을 것
홈페이지를 새로 구축할 때, 아이디어나 화면 디자인이 떠오르면 바로 프레임워크를 셋업하고 코드를 작성하는 흥분감에 먼저 빠져들었다.
그 결과, 로컬 작업물이 쌓인 상태에서 뒤늦게 깃허브를 연결하려다 브랜치 히스토리 충돌(unrelated histories), 불필요한 빌드 파일 커밋 혼입 등으로 인해 세팅을 엎고 두 번 작업하는 낭비가 발생했다.
**다시 한다면 — 코드를 단 한 자도 치기 전에, 빈 GitHub 리포지토리 생성과 로컬 `git remote add`를 0단계로 먼저 못박을 것이다.**

### 2. `.gitignore`를 프레임워크 템플릿보다 먼저 검증했을 것
깃허브 세팅이 늦어지면 `node_modules`나 `.next`, 환경변수 `.env` 파일이 인덱스에 잡히기 쉽다.
사후에 캐시를 지우고 되돌리는 수고를 겪느니, 프로젝트 폴더를 만들자마자 `.gitignore`부터 정립하는 것이 훨씬 빠르고 안전하다.

## 이 후회가 남긴 불변의 원칙

> **"모든 웹 프로젝트의 시작은 코딩이 아니라 GitHub 연결이다."**

- GitHub 리포지토리는 단순한 백업 공간이 아니라, **프로젝트의 생명선이자 배포 파이프라인(CI/CD)의 출발점**이다.
- 리포지토리 생성 ➔ `git init` ➔ 첫 커밋 ➔ 배포 파이프라인 연결이 5분 안에 끝나야 본 개발이 맑고 투명하게 뻗어나갈 수 있다.
