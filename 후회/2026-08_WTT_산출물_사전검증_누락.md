## 1. 무엇을 후회하는가? (The Regret)

WTT(통합 워크스루 테스트)를 수행하면서 Python 단위/통합 테스트 스크립트(`run_wtt_tests.py`)가 100% 통과했다는 이유만으로, **정작 사용자에게 전달되는 배포 산출물(`.sql` 시드 파일) 자체를 실서버 DB에 직접 실행(Dry-Run)해보지 않고 최종 승인을 내린 치명적인 검증 사각지대**를 발생시켰다.

이로 인해 사용자가 실제 DB에 SQL을 주입할 때 외래키 부재, 컬럼명 불일치(`company_name`), `VARCHAR(20)` 길이 초과 에러가 연쇄적으로 터지는 수치스러운 결함을 초래했다.

---

## 2. 왜 발생했는가? (근본 원인 해부)

1. **테스트 객체와 배포 산출물의 이원화 (Disconnection)**:
   - 메모리 상의 파이썬 테스트 코드는 통과했지만, 파일로 내보낸 SQL 생성기(`generate_wtt_mock_sql.py`)의 쿼리는 실제 스키마 DDL(`domain.py`)과 어긋나 있었다.
2. **SSOT(단일 진실의 원천) 무시 및 수동 하드코딩**:
   - `domain.py` 모델을 리플렉션하지 않고 과거 엑셀 명칭을 관성적으로 하드코딩하여 스키마 드리프트가 발생했다.
3. **'배포 전 최종 Dry-Run'이라는 기본 철칙 생략**:
   - "테스트가 통과했으니 SQL도 맞겠지"라는 안일한 가정이 화를 불렀다.

---

## 3. 감사 SA의 엔지니어 SA에 대한 공식 경고

> **"엔지니어 SA는 명심하라. 테스트 러너가 초록색(PASS)을 띄웠다고 해서 개발이 끝난 것이 아니다.  
> 최종 사용자의 손에 쥐어질 '배포 산출물 자체'가 실제 대상 환경에서 0 Error로 실행되는 것을 두 눈으로 입증하기 전까지는, 그 어떤 코드도 '완료'나 '승인'을 입에 담을 수 없다."**

---

## 4. 영구 재발 방지 철칙 (Global WTT Rule)

- **원칙**: 모든 WTT 파이프라인의 최종 관문은 **"배포용 파일 자체를 실제 타겟 DB에 직접 실행하여 0 Error 로그를 증명하는 것"**으로 영구 고정한다.
