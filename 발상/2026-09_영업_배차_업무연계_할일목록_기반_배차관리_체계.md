## 1. 발상의 배경 및 문제 인식

### 1.1 기존 배차관리의 한계 (대장 중심 수동 입력 방식)
- 기존 배차관리 화면은 단순한 전체 배차 테이블(그리드)과 수동 등록 버튼 중심으로 구성되어 있었음.
- 이 방식에서는 배차담당자가 **"지금 당장 어떤 영업사원이 어떤 현장에 몇 시까지 차를 보내달라고 했는가?"**를 확인하기 위해 계약 대장이나 출고요청 화면을 번갈아 확인하거나, 메신저/유선 통화에 의존해야 하는 이중 조작의 비효율이 발생함.

### 1.2 업무 파이프라인의 본질: "모든 업무는 의뢰에 의해 발생한다" (헌장 2.3)
- 배차 업무는 독립적으로 독자 발생하는 것이 아니라, **영업사원이 고객사와 계약을 체결하고 장비 출고/회수/교환을 의뢰하는 사건(Event)에서 촉발**됨.
- 따라서 배차담당자의 본질적인 직무는 **"영업부에서 발행된 배차 의뢰를 접수하여, 적합한 화물차량과 기사를 수배하고, 운송비를 확정하여 완결하는 것"**임.

## 2. 핵심 발상: ToDo(할일 목록) 기반 배차 파이프라인

### 2.1 영업 ➔ 배차 간 3단계 직무 체인
1. **[Step 1: 의뢰 발행 (영업부)]**:
   - 영업사원이 계약 등록, 출고요청, 회수요청, 대차/교환요청을 접수/발주.
   - 시스템은 `deliveries` 테이블에 `status: 'REQUESTED'` 상태로 배차 의뢰를 자동 인입.
2. **[Step 2: ToDo 피드 큐 적재 (배차담당자)]**:
   - 배차담당자의 화면(PC `TruckDispatch`, 모바일 `MobileDispatchList`) 최상단에 **"오늘 처리할 배차 할일 목록 (ToDo / 의뢰 접수 큐)"**이 실시간 카드로 노출.
   - 각 카드에는 영업사원명, 의뢰유형(출고/회수/교환), 현장명, 납기일시, 요청 장비 제원 및 대수, 현장소장 연락처, 특이 메모가 1눈에 조망됨.
3. **[Step 3: ToDo 실행 및 완결 (배차담당자)]**:
   - 배차담당자가 ToDo 카드를 선택하면 기사 배정 팝업/패널이 즉시 열림.
   - 기사/차량/운송료를 매핑하고 `[배정 확정]` 또는 `[배정 확정 + 문자 즉시 발송]`을 누르면:
     - 상태가 `'DISPATCHED'`(배차완료)로 전이.
     - 해당 건은 배차담당자의 '할일 목록'에서 즉시 제거(완결)되어 잔여 할일 카운트가 실시간 차감.
     - 기사에게는 배차 안내 문자가 원클릭 발송됨.

### 2.2 임의 배차 추가 기능의 공존 (예외 운송 지원)
- 영업사원의 계약 의뢰와 무관하게 발생하는 주기장 간 장비 이동, 공장 입고 정비, 긴급 수동 배차 등은 기존의 `[+ 신규 배차 등록]` 기능으로 언제든지 담당자가 직접 임의 입력할 수 있도록 100% 동일하게 유지.

## 3. 기대 효익 및 향후 구현 방향

1. **임직원 조작 최소화 (헌장 1.1)**:
   - 배차담당자는 출근 후 또는 외근 중 자신의 '할일 목록'만 확인하면 오늘 처리할 배차 건이 명확히 정렬되어 있어, 누락이나 혼선이 원천 차단됨.
2. **부서 간 R&R 완벽 정합 (헌장 2.1)**:
   - 영업부는 '출고/대차 의뢰'까지만 담당하고, 배차담당자는 '의뢰 접수 후 차량 배정'을 완결하여 부서 간 책임 소재가 명확히 분리됨.
3. **UI 아키텍처 정립 (헌장 3.3, 3.6)**:
   - PC 및 모바일 화면에 '할일 목록(ToDo / 배차 대기)' 섹션과 '전체 배차 대장' 섹션을 유기적으로 결합하여, 업무 개시점(ToDo)과 마감/정산점(대장)의 Z-패턴 동선을 완성.
