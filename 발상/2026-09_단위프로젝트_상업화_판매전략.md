# 발상 | 단위 프로젝트 상업화(Monetization) 및 플랫폼 판매 전략

> **타임스탬프**: 2026-09-12
> **연결**: 이 발상 → 상용화 파이프라인 계획 → 실제 판매 경험

---

## 1. 발상의 순간
> "내 프로젝트들 중 다양한 플랫폼에서 판매할만한 단위 프로젝트가 생긴다면 어떻게 판매해야 할까?"
> — 사장님, 2026-09-12

내부 자동화, AI 분석, RPA를 위해 구축된 모듈형 '단위 프로젝트'들을 B2B/B2C 상용 제품으로 패키징하여 새로운 수익 창출 파이프라인으로 전환하려는 전략적 구상.

---

## 2. 판매 방식에 따른 3대 아키텍처

내부 시스템은 '우리'만 쓰면 되지만, 판매용 시스템은 **배포, 인증, 결제, 보안**이 추가되어야 한다. 단위 프로젝트의 특성에 따라 다음 3가지 경로 중 하나를 선택한다.

### ① 설치형 데스크톱 앱 (B2B Local App)
- **적합한 프로젝트**: 한컴 HWP 자동화, 엑셀 COM 자동화, 로컬 GPU를 쥐어짜는 Video_Create_Studio 등 보안이나 로컬 리소스가 필수적인 작업.
- **패키징 기술**: Python 코드를 `PyInstaller` 또는 `Nuitka`로 컴파일(.exe)하여 소스코드 유출(리버스 엔지니어링) 방지. UI는 PyQt 또는 Tauri 활용.
- **인증/라이선스**: 앱 실행 시 서버와 통신하여 구독/라이선스 유효성을 검증 (예: HWID 바인딩).

### ② API 서비스 (BaaS, Backend as a Service)
- **적합한 프로젝트**: AI 분석 파이프라인, 음성 화자 분리, PDF 대용량 병합 등 "데이터를 넣으면 결과를 반환하는" 순수 논리/AI 모듈.
- **패키징 기술**: FastAPI로 감싸서 서버(또는 Vercel/AWS)에 배포.
- **판매 방식**: API 호출 횟수당 과금 (Pay-as-you-go).

### ③ SaaS (Web Application)
- **적합한 프로젝트**: 사용자 친화적인 대시보드가 필요한 도구 (예: 사업자등록증 고객등록 자동화 웹버전).
- **판매 방식**: 월간/연간 구독 모델(Subscription).

## 3. 플랫폼 및 결제망 (어디서 팔 것인가?)

1. **소프트웨어 라이선스 & 다운로드 판매**
   - **LemonSqueezy (레몬스퀴지)**: 글로벌 결제, 라이선스 키 발급 및 검증 API 기본 제공. (현재 글로벌 소프트웨어 판매 1티어)
   - **Gumroad (검로드)**: 진입 장벽이 가장 낮음. 스크립트(.py, .bat), 템플릿, 간단한 유틸리티 묶음 판매에 최적.
2. **API 스토어**
   - **RapidAPI**: 개발한 API를 올려두면 글로벌 개발자들이 구독하고 호출당 결제.
3. **국내 B2B/프리랜서 마켓**
   - **크몽 / 숨고**: 'RPA 구축', 'HWP/엑셀 자동화 툴' 형태로 B2B 맞춤형 판매. (단가 방어에 유리)

---

## 4. 상용화를 위한 기술적 "분리(Decoupling)" 과제

현재 사내 프로젝트는 사내 DB 구조와 글로벌 정책(`system_install_log.md`, 텔레그램 허브 등)에 강하게 결합되어 있을 가능성이 높습니다. 판매를 위해서는 **종속성 끊기**가 필요합니다.

1. 사내 전용 환경변수/토큰(예: Cloudflare R2 `drcf` 계정) 걷어내고 사용자 설정창(Config) 주입 구조로 변경.
2. 무음 실패(Silent Failures) 발생 시 사내 에러 로그가 아닌, 사용자 친화적 에러 UI 제공.
3. 무단 복제 방지 로직 (코드 난독화 및 라이선스 서버 체크).
