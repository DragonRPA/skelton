## 발상의 순간

ConsultParser2 분석 탭을 보면서 사장님이 지적하셨다:

> *"표시되어야 하는 프로세스 진행사항에 대해서 가중치를 판단할 때,
> 현재의 상황에 대해서 중요도가 낮은 절차에 대해서 너무 많은 비중을 할애하고 있지 않은가?
> 프로세스를 중요도별로 scoring 하여 합리적인 UI 디자인이 도출되어야 할것 같아."*

---

## 핵심 발상

> **"UI 공간은 비즈니스 가치에 비례해야 한다. 프로세스의 순서가 UI의 비중을 결정하면 안 된다."**

현재 대부분의 파이프라인 UI는 절차 순서(1단계→2단계→3단계)를 그대로
시각적 계층에 옮긴다. 그러나 절차의 순서는 기술적 의존 관계이지,
비즈니스 가치의 순서가 아니다.

---

## 왜 이것이 문제인가

### 현재 ConsultParser2 UI 공간 배분 (비판적 분석)

| 요소 | 현재 시각 비중 | 실제 비즈니스 가치 | 불일치 |
|------|-------------|----------------|--------|
| 1단계 버튼 (스키마 정규화) | 대형 풀폭 버튼 | 하 — 기계적 전처리, 5분 | 과다 |
| 2단계 버튼 (AI 군집화) | 동일한 대형 버튼 | 최상 — 핵심 가치 창출 | 과소 |
| 진행 로그 | 작은 텍스트 | 상 — 75분 동안 가장 중요한 정보 | 과소 |
| 결과물 탭 (대시보드/CSV) | 하단 소형 탭 | 최상 — 이것이 목적 | 과소 |
| 폴더 경로 입력 | 상단 전폭 | 하 — 초기 1회 설정 | 과다 |

## 원칙 정립

### UI 중요도 Scoring 모델
```
Score 10: 최종 결과물 — 대시보드, CSV, FMEA (왜 이 시스템을 쓰는가)
Score  8: 핵심 처리 진행 상황 — AI 군집화 실시간 진행률
Score  7: 핵심 실행 액션 — 2단계 실행 버튼
Score  4: 입력 설정 — 폴더 선택, 파일 목록
Score  3: 전처리 액션 — 1단계 실행 버튼
Score  1: 완료된 절차 — 이미 끝난 단계 (최소화)
```

### 적용 원칙
1. **결과가 존재할 때** — 결과물이 UI의 최대 면적을 차지해야 한다
2. **처리 중일 때** — 진행 상황이 가장 두드러져야 한다
3. **대기 중일 때** — 다음 행동 단계만 강조, 나머지는 축소
4. **완료된 단계** — 접힘(Collapse) 또는 시각적 최소화

---

## 다른 실무 관점과의 경합

이 원칙은 다음 실무 관점과 충돌할 수 있다:
- "절차를 순서대로 보여줘야 사용자가 현재 위치를 안다" (프로세스 투명성)
- "모든 단계 버튼을 항상 노출해야 수동 재실행이 가능하다" (접근성)

**해결 방향**: 중요도 낮은 요소는 제거가 아니라 **축소(Collapse)** — 필요할 때 펼칠 수 있되, 기본 상태에서는 작게.
