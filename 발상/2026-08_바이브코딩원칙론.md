## 발상의 순간

유튜브 강의를 수집하고 분석하는 과정에서, 외부 세계가 우리가 skelton으로
구현하려는 것과 완전히 같은 개념을 독립적으로 정립했다는 것을 발견했다.

> *"일회성 질문에 그치는 '빌리는 지능'과 작업의 흔적·맥락·성공 기준을 자산화하여
> 복리적으로 성장하는 '쌓이는 지능'의 개념적 차이."*

skelton은 **쌓이는 지능의 물리적 구현체**였다.

---

## 핵심 발상 1 — 빌리는 지능 vs 쌓이는 지능

> **"매번 새 채팅창을 여는 것은 어제의 나를 버리는 것이다."**

| 구분 | 빌리는 지능 | 쌓이는 지능 |
|------|-------------|-------------|
| 방식 | 새 채팅창, 복사-붙여넣기 | 의사결정 기록, 맥락 주입 |
| 성장 | 휘발. 매번 제로에서 시작 | 복리. 이전 판단이 다음을 강화 |
| 자산 | 없음 | 파일·구조·레포로 축적됨 |
| 예시 | "이 코드 고쳐줘" | skelton 4대 사이클 기록 |

**skelton은 바로 이 '쌓이는 지능'의 인프라다.**
발상·계획·경험·후회 각각이 다음 판단의 컨텍스트로 주입된다.

---

## 핵심 발상 2 — 딥트윈(Deep Twin)과 skelton의 동형성

> **"사람을 카피하는 것이 아니라, 검증된 판단의 궤적을 기계화하는 것."**

딥트윈 프레임워크의 3층 구조:
```
Core Knowledge (기초 지식)       → 글로벌 정책 (user_global)
Human Experience (개인 노하우)   → 경험.md + skelton 경험 폴더
Workflow Mapping (단계별 분화)   → 발상→계획→경험→후회 사이클
```

우리는 이미 딥트윈을 만들고 있었다. 이름만 몰랐을 뿐.

---

## 이 발상이 확인해 준 것

- skelton 레포의 4대 사이클 구조가 **외부에서도 검증된 보편 원칙**임
- "빌리는 지능"에 머무는 바이브 코딩과 "쌓이는 지능"을 구축하는 바이브 코딩의 차이는
  **레포 하나**에서 갈린다
- 5년 후 이 skelton을 열었을 때, 그것이 딥트윈의 완성형이 되어 있을 것

## 핵심 발상 3 — 데모 이후의 무너짐은 설계 순서의 문제다

> **"바이브 코딩의 데모는 항상 성공한다. 그 다음이 문제다."**

강의에서 제시한 6단계 대시보드 설계 프레임워크를 처음에는
"대시보드 특화 실무 지침"으로 판단해 미채택했다.
그러나 재검토하니, 핵심은 **단계 순서 자체가 사고의 순서**라는 점이었다.

**역방향 바이브 코딩 (대부분의 실패 패턴)**:
```
코드 (딸깍) → UI (예쁘다!) → 배포 (데모 성공!)
                                    ↓
              두 번째 요구사항 → 전체 재작성
```

**순방향 설계 (지속 가능한 구조)**:
```
문제(KPI/병목) → 데이터(스키마·상태) → 구조(IA) → 시스템(API) → UI → 코드
```

데모 이후 무너지는 이유는 기술 부채가 아니다.
**데이터 구조와 업무 흐름을 정의하기 전에 화면을 먼저 만들었기 때문이다.**

두 번째 요구사항이 들어오는 순간, 첫 번째 화면의 가정이 전부 틀렸음을 깨닫는다.
이것은 바이브 코딩의 한계가 아니라 **순서를 건너뛴 대가**다.

### 앞으로의 프로젝트에 적용할 판단 기준

새 프로젝트 착수 시, 코딩 전에 다음 두 가지가 문서로 존재하는가:
1. **KPI / 병목**: 이 시스템이 해결해야 할 비즈니스 문제가 한 문장으로 정의되었는가
2. **데이터 상태 정의**: 핵심 객체의 상태(State)값 목록이 테이블로 존재하는가

이 두 가지가 없으면, 아무리 빠르게 만들어도 두 번 만드는 것과 같다.
